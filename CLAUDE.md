# Luca van Ruiten — Photography Portfolio

Handoff notes for continuing this project in a future session. Read this before making changes.

## What this is

A static portfolio website for **Luca van Ruiten**, a queer photographer based in Rotterdam (portrait, studio, analog, social documentary). Built from a brief in `~/Desktop/prompt new website.rtf` (on the user's machine, outside this repo). Hosted on **GitHub Pages** with a custom domain (`CNAME` → `lucavanruiten.com`, apex, no `www` — see "Domain: apex, not www" below for why). No backend, no build step, no framework — plain HTML/CSS/JS on purpose, so the user can host it with nothing but a `git push`.

**Status: nothing in this rebuild has been committed yet.** The entire site (all pages, CSS, JS, generated images) exists only in the working tree on `main`. The old site's files show as deleted in `git status` (not staged). Before this can go live, someone needs to `git add`/`commit`/`push` — do not do this unprompted, ask the user first per standing instructions.

## Internationalization (English / Dutch)

The user asked for the whole site to exist in both English and Dutch, primarily for SEO (so the site can be found in Google under either language), with visitors able to pick either. Implementation, chosen with the user over the alternatives (query param, `-nl.html` suffix, JS-only toggle):

- **`/nl/` subfolder mirrors every page** — `nl/index.html`, `nl/projects.html`, `nl/project-queer-scene.html`, `nl/project-escape.html`, `nl/project-people.html`, `nl/dump.html`, `nl/contact.html`, `nl/404.html`. Each is a fully separate, crawlable URL (not a client-side toggle over one URL) — this matters because Google indexes language variants by URL, not by JS-rendered state.
- Every `nl/*.html` references shared assets one level up (`../css/style.css`, `../js/main.js`, `../favicon.png`, `../images/...`) rather than duplicating them. Internal nav links between `nl/` pages stay relative within `nl/` (e.g. `nl/index.html`'s "Werk" link is `projects.html`, not `../projects.html`) — only the language-switcher link and the `<link rel="alternate" hreflang>` tags cross between the two trees.
- **Language switcher**: a small "EN"/"NL" text link with class `.lang-switch` (styled in `style.css` right after `.nav-toggle` — dimmed to `opacity:.55`, full opacity on hover/focus) sits at the end of `.nav-links` on every page, pointing at the exact counterpart page in the other language. If you add a 9th page, add its switcher link both directions and don't forget the `hreflang`/`lang` attributes on the `<a>` itself.
- **Every page (both languages) carries**: `meta description`, `meta author`, `meta robots` (`index, follow`; `noindex, follow` on both 404 pages only), a self-referencing `link rel="canonical"`, three `link rel="alternate" hreflang` tags (`en`, `nl`, and `x-default` — `x-default` always points at the **English** URL, matching the original live site's own convention), Open Graph tags (`og:locale` is `en_NL` on English pages, `nl_NL` on Dutch ones), Twitter Card tags, and a page-appropriate JSON-LD block (`Person` for index/contact, `CollectionPage` for projects, `ImageGallery` for the gallery projects and dump, `Book` for escape — these types were carried over from the original live site's own structured data, see below).
- Dutch copy was translated fresh for this rebuild (not machine-copied from the old site, which never actually had Dutch pages built — see below) — translated by Claude, matching the existing English copy's tone. If the user wants to hand-edit the Dutch wording later, treat their edits as authoritative the same way `contact.html`'s English bio is treated as the user's own voice.
- **One real bug this surfaced and fixed**: `initHeroImages()` in `js/main.js` used to build its hero-photo source list as `images/index_animations/web/image${i+1}.webp` — a *document-relative* path. That resolves fine from a page at the site root, but from `nl/index.html` (one directory deeper) the browser would have requested `nl/images/index_animations/web/...`, which doesn't exist, silently breaking the hero photos on every Dutch page. Fixed by making it root-relative (`/images/index_animations/web/...`) instead, which works from any page depth. This is the only hardcoded image path inside `main.js` itself — everything else is written into each page's own HTML (already given correct relative depth per page) or resolved via CSS (which resolves relative to the stylesheet's own URL, not the page's, so `css/style.css` needed no changes).
- **`robots.txt`** and **`sitemap.xml`** were added at the repo root (previously missing from this rebuild entirely) — modeled on the ones in `ORIGINAL WEBSITE (NOW LIVE)/`, which already anticipated `/nl/` URLs in its own hreflang tags and sitemap even though those Dutch pages were never actually built on the live site. `sitemap.xml` lists all 16 URLs (8 EN + 8 NL, `404.html` intentionally excluded since it's `noindex`) with `xhtml:link` hreflang alternates on every entry.
- **Where the SEO groundwork came from**: `ORIGINAL WEBSITE (NOW LIVE)/` (see Structure above) is a snapshot of the actual pre-rebuild live site, kept in the repo purely as an SEO/copy reference — it already had per-page meta descriptions, OG/Twitter tags, JSON-LD, canonical URLs, and hreflang scaffolding for a Dutch version that was never built. This session ported that metadata (updated for the new page names/structure) onto the rebuild rather than starting from scratch, then improved a few descriptions and added JSON-LD where the old site had none (`dump.html`'s old equivalent, `messy_grid.html`, had no structured data). That folder is not part of the deployed site — don't reference it from any live page, and don't delete it without asking (it's the user's own SEO record of what used to work).

## Design system (important: read before restyling)

Every color on the site is a CSS variable, resolved with `color-mix()` where derived. **To retheme the whole site, only a handful of variables need to change**, at the top of `css/style.css`:

```css
:root{
  --bg: #040000;       /* page background — the site now ships DARK by default */
  --accent: #0efafa;   /* accent color — cyan as of this session; was #ff46ac (pink) before */
  /* --bg-raised, --accent-deep, --accent-soft are auto-derived via color-mix() */
}
```

This is exactly how the dark/light toggle works (see below) — it's a proof the variable system holds up. Note the default theme flipped from the original light brief colors (`--bg:#f6f2ec`, `--accent:#5b46ff`) to dark sometime in an earlier session; the original light palette now lives under `html.light-mode` instead of at `:root`.

**Known inconsistency, not yet resolved:** `html.light-mode` still hardcodes `--accent:#ff46ac` (the old pink), independently of `:root`'s `--accent`, so switching to light mode currently also switches the accent color back to pink rather than keeping whatever `:root` says. Nobody's asked to fix this yet — flag it if you're touching either theme block, since it's unclear whether light mode should track `:root`'s accent or deliberately keep its own.

The custom cursor (`.cursor-dot`, `.cursor-ring`, see below) reads `--accent` too, so it changes with the theme. Its `mix-blend-mode:difference` means the color you actually see is difference-blended against whatever's under the pointer, not the literal accent color — that's an existing, deliberate tradeoff (it's what keeps the cursor visible over both photos and either theme's background), not a bug.

- **Fonts**: Space Grotesk (bold, headlines/labels/nav) + Inter (body copy). Loaded via Google Fonts `@import` at the top of `style.css`. The user explicitly rejected a serif (Fraunces) — do not reintroduce serif/italic styling without asking.
- **No italics anywhere** — emphasis is done with `--accent` color + bold weight, not `font-style:italic`.
- Page transitions use the **native View Transitions API** (`<meta name="view-transition" content="same-origin">` in every `<head>` + `::view-transition-old/new(root)` keyframes in CSS — a combined slide + fade + subtle scale, see `lvr-page-out`/`lvr-page-in` in `style.css`). Zero JS. Degrades gracefully (silently, no fallback code needed) in browsers without support — an unsupported browser just does a normal instant navigation.
- **Page loader** (`.page-loader`, first element in every `<body>`, hidden by `initPageLoader()` in `main.js` on `window.load`) covers the page until it's actually finished loading, masking a slow/"buffering" connection instead of showing a half-loaded page. It's intentionally text+CSS only (no image/font it has to wait on itself) so it still appears immediately on the exact bad-wifi conditions it exists for. Because it's duplicated markup at the top of every page (like nav/footer — see below), it also naturally reappears on every cross-document navigation, so it "just works" with the view-transition system above with zero extra wiring: the incoming page (loader included) slides/fades in per the view-transition keyframes, then a moment later the loader's own fade-out runs once that page's `load` fires. If you change the loader markup, **update it in all 8 HTML files** (grep `class="page-loader"`), same rule as nav/footer.

## JS features (all in `js/main.js`, one IIFE, run on `DOMContentLoaded`)

- `initPageLoader()` — hides `.page-loader` (see below) on `window.load`, with a 400ms minimum display time (so a fast local load doesn't just flash) and a 5s safety-net timeout in case `load` never fires. Runs first in the init list, though order doesn't matter functionally — it only registers a listener.
- `initShuffle()` — Fisher-Yates shuffles `.dump .dump-scatter` children before anything else runs, so which photo lands in which cell of the scatter layout (and lightbox next/prev order) varies per load. **Must stay first** in the init list, before `initDumpScatter()`.
- `initDumpScatter()` — randomizes size/position/rotation/stacking for every `.dump-item` on `dump.html` and wires up its drag-and-throw. See "Dump page — scattered pinboard" below for the full mechanic.
- `initCursor()` — custom dot+ring cursor, `mix-blend-mode:difference`, desktop only (`hover:hover and pointer:fine`). Hoverables are matched via `a, button, .grid-item, [data-cursor]` — add `data-cursor="Label"` to any element to get a labeled ring on hover. The native OS cursor is fully suppressed on the same media query (`*{ cursor:none !important; }` in `style.css`) so only this designed cursor is ever visible on hover-capable/fine-pointer devices; touch/coarse-pointer devices fall back to the normal system cursor since the custom one is hidden there too (`@media (hover:none), (pointer:coarse)`).
- `initNav()` — hide-on-scroll-down nav, mobile hamburger toggle.
- `initReveal()` — IntersectionObserver fade-up for any `[data-reveal]` element, staggered by sibling index.
- `initHeroImages()` — **generates** the landing-page hero figures entirely in JS (there's no hardcoded `.float-img` markup in `index.html` any more — `.hero-float` starts empty). How many it makes is controlled by two constants at the top of this function: `HERO_IMAGE_COUNT_DESKTOP` and `HERO_IMAGE_COUNT_MOBILE` (kept deliberately separate per the user's request — a phone-sized count of the desktop's density would be cramped), switched on `window.innerWidth <= HERO_MOBILE_BREAKPOINT` (780, matching this page's other mobile breakpoints) — **this is a deliberate experimentation knob the user asked for**, to try different densities on the hero before settling on a final count. The user has already been changing `HERO_IMAGE_COUNT_DESKTOP` directly between sessions (seen values from 20 to 200) — don't "clean it up" into a fixed value, and don't be surprised if it's not whatever this doc last mentioned; check the file for the current number rather than assuming. Source photos (replaced Sept 2026, picked from Dutch Queer Scene and its Beauty — both sub-galleries) are **8 portrait** (`images/index_animations/web/portrait-1..8.webp`, 600×900) **+ 4 landscape** (`landscape-1..4.webp`, 900×600), counts set by `HERO_PORTRAIT_COUNT` / `HERO_LANDSCAPE_COUNT`. Each pool is shuffled once per load, and every frame draws from the pool matching its template's shape (`aspect > 1` → landscape, else portrait — mobile's square frames take portraits), so photos are never cropped into the wrong orientation. The desktop templates hold 8 portrait + 4 landscape frames in 12, so at a count of 12 each photo appears exactly once; repeats only start above that. If you add photos, keep them exactly 2:3 / 3:2 and bump the matching count constant. Position is a loose grid (`cols`/`rows` derived from `count`) with random jitter per item so it doesn't read as a rigid grid, and size/aspect ratio cycle through a small hand-picked template list (separate lists for desktop vs. mobile). Each image's computed box is also checked against a `keepClear` zone measured from the real `.hero-content` element (not a guessed percentage — the name's font-size is `clamp()`-capped, so a hardcoded box came out narrower than the actual text at some viewport widths) and pushed just outside it on whichever axis has room if it would overlap; see `initHeroFloat()` below for why this alone isn't sufficient and what also runs continuously during wander. Separately, every image's `top` is also clamped below `navBottomPct` — the real rendered bottom edge of `.site-nav`, converted to a percentage of the hero's height — so nothing can land at, say, `top:0%` and render directly behind the fixed nav bar. This exists because `.site-nav` relies on `mix-blend-mode:difference` for its text color (see below) rather than a fixed color, and that trick only produces a clean, legible invert when what's behind it is the hero's own plain background — a photo there makes the blended color muddy and unpredictable per pixel, which is what the user meant by "the nav isn't very readable." `.hero-float` is `position:absolute; inset:0` covering the *entire* `.hero` section (the `padding-top:var(--nav-h)` on `.hero` only shifts `.hero-content`, not this layer), so nothing previously stopped an image from sitting in that strip. Must run before `initHeroFloat()` in the init list, since that function just operates on whatever `.float-img` elements already exist in the DOM. The old approach (hand-authored `.float-img.f1`..`.f9` CSS classes, one fixed position per image) is gone from `style.css` — it couldn't scale to an arbitrary count. Mobile images additionally get a `.float-img--mobile` class (`opacity:.55` in `style.css`) for the same dimmed-texture look as before.
- `initHeroFloat()` — the landing-page hero images. Each image is a small physics body: continuous organic "wander" (slowly-turning heading, not literal noise), a soft spring pulling it back toward its CSS resting position within `maxRadius`, a proximity-based "kick" when the cursor passes near it, and full **pointer-based drag-and-throw** (grab an image, it follows 1:1, release it and it keeps the throw velocity). Tunable constants are declared at the top of the function (`maxRadius`, `wanderStrength`, `kickStrength`, `damping`, `flingCap`, etc.) — the user has asked to tune this a few times already (bigger movement, then bigger images + drag), so expect more tuning requests; adjust constants rather than rewriting the approach. Doesn't care how many `.float-img` elements exist or how they got there — `initHeroImages()` (above) now owns generating them. `.hero-float` carries `z-index:1; isolation:isolate` so a dragged image's temporary `z-index:5` (set/cleared in the pointerdown/release handlers here) is contained inside that stacking context and can never render above `.hero-content` (`z-index:2`) — this is what keeps a thrown image from glitching in front of the name, no matter how many images there are. Don't remove the `isolation:isolate` without re-testing a drag over the name.
  - **Steers clear of the name/subtitle continuously, not just at initial placement.** `.hero-content`'s box (measured live via `getBoundingClientRect`, plus a `textPushMargin` buffer) is checked every frame against each image's *current* position and half-size (`item.restX/restY` — the resting center captured once at setup — plus its live `item.x/item.y` offset, so this needs no per-frame `getBoundingClientRect` call). Any image whose box overlaps it gets a continuous push (`textPushStrength`) directly away from the box center, same idea as the cursor "kick" but ongoing rather than a one-off dart. This exists because ambient wander alone (drifting up to `maxRadius` from a resting spot) can carry an image across the text over time even if `initHeroImages()` placed it clear to start with — a purely one-time placement fix regressed to "images sit behind the text all the time" once there were enough of them wandering for one to eventually drift across it. Check must be a true rectangle-overlap (image half-width/half-height included), not just a center-point-in-box check — a center-only check let large images still visually clip the text edge while technically "clear."
  - **Steers clear of the fixed nav the same way**, via `navBottom` (the nav's real rendered bottom edge, plus a `navPushMargin` buffer) and `navPushStrength`. Unlike the text box this is a one-sided check (`top < navBottom`, no left/right/bottom) and the push is straight down (`item.vy += navPushStrength * dt`, no `atan2`) rather than away from a center point — the nav spans the full viewport width, so there's no horizontal direction that would ever actually clear it, only downward does. This is what fixes the nav readability problem end to end: `initHeroImages()` keeps every image's *starting* position out from behind the nav, and this keeps wander/drag from carrying one back up into it afterwards.
- `initLightbox()` — builds one lightbox instance, scans every `[data-lightbox-group]` container independently (so e.g. the two sub-galleries on the queer-scene page have separate next/prev sequences). Uses `data-full` attribute on each `<img>` for the high-res source; grid `src` stays on the compressed version.
- `initThemeToggle()` — see below.

## Dump page — scattered pinboard

`dump.html` was rebuilt from a masonry grid into a chaotic, draggable pile (the user's explicit direction: "the other parts of the site have to be somewhat neat, but the dump page can be chaotic... make it like a real dump"). Three concepts were pitched (pinboard scatter / rogue bento / print pile + contact strip); the user picked pinboard scatter.

- Markup: `.dump-scatter` (was `.gallery-grid`) contains 36 `<figure class="dump-item">` (was `.grid-item`), each just an `<img data-full="...">` as before — no other markup changes, and **the image list/alt text was left untouched** (the user was mid-edit on site copy when this shipped; don't touch text in this area without asking).
- Layout is entirely computed by `initDumpScatter()` in `main.js`: on every page load it picks a random width, aspect ratio (from a fixed list — portrait/landscape/square/tall/wide), position (jittered off a coarse grid so photos overlap without fully clumping), rotation (±13deg), and stacking order (random z 1..36) for every item, then writes them as inline styles (`left`/`top`/`width`/`height`/`--r` custom property). Refreshing the page reshuffles all of it — there's no seed, it's genuinely different every load. `initShuffle()` (still first in the init list) randomizes DOM order first, so which photo lands in which cell also varies per load.
- Rotation is applied via `transform:rotate(var(--r))` in CSS (not written inline as `transform` directly) specifically so `.dump-item:hover` can override it with a plain CSS rule (straighten + lift + scale on hover) without fighting inline-style specificity.
- Every item is grab-and-throw draggable, same pointer-events approach as the landing-page hero (`initHeroFloat()`) — see JS features above — but deliberately **without** the hero's idle wander/spring/cursor-kick: with 36 large images instead of 9 small ones, continuous ambient animation across the whole page would fight scrolling/reading rather than feel playful. Drag physics use a per-item `translate` offset from the item's static `left`/`top`, clamped to the stage's own bounds (`clamp()` inside the per-item closure), and on release the item coasts to a stop via its own short-lived `requestAnimationFrame` loop (not a persistent global loop like the hero's — cheaper, since idle items cost nothing).
- Dragging vs. clicking-to-open-lightbox is disambiguated by movement distance: past a 6px threshold from pointerdown, `initDumpScatter()` marks `el.dataset.suppressClick = "1"`, and `initLightbox()`'s click handler checks and clears that flag before deciding whether to open. A dragged item's picked-up z-index is *not* reset back to its original random value on release — it's promoted via a monotonically increasing `topZ` counter (starting at 100, capped conceptually below the nav's z-index of 500) so a dropped photo stays on top of whatever it landed on, matching how a real print would behave.
- `--frame-bg` / `--frame-shadow` / `--frame-shadow-hover` (dark-mode-adapted polaroid frame tokens, from an earlier session) still apply to `.dump-item` unchanged — see the tokens block near the top of `style.css` and the `html.light-mode` override near the bottom; keep both in sync if you touch the frame look.

## Local dev / verification

`.claude/launch.json` defines a `static-site` config (`python3 -m http.server 8642`) for the Browser-pane preview tools, plus a `static-site-verify` config on port 8643 — use the second one if another session/chat already has `static-site` running, since the Browser pane can't reach a server started outside its own session. Two gotchas discovered in an earlier session:
1. Python's `http.server` sends no cache headers, and the preview browser can cache `main.js`/`style.css` aggressively across `navigate()` calls to the same URL. If a JS/CSS change doesn't seem to take effect, **append a changing query string** (`?cb=2`, `?cb=3`, ...) rather than assuming the code is wrong.
2. `[data-reveal]` elements are invisible (`opacity:0`) until scrolled into view — a screenshot taken immediately after navigation can look blank even though everything is correct. Wait ~1s or scroll before judging a screenshot.
